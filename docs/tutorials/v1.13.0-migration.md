# Migrating to v1.13

Every node on a v1.12.x release should move to the latest v1.13 release, and track releases at
[`ethereumclassic/core-geth`](https://github.com/ethereumclassic/core-geth). **From `v1.12.17` on, a resync is not part
of the upgrade:** your chain data carries over. A node on an older release
[resyncs instead](#if-the-node-runs-a-release-before-v11217). Budget about twenty minutes for the steps. The node is
down from step 1 to step 5, though stopping and starting it usually take seconds.

A `v1.12` node that cannot move yet can
[add the `--discovery.dns` flag](../etc-cooperative-transition.md#if-a-v112-node-cannot-move-yet) to read the
`ethereumclassic` organization's peer discovery lists, a small step that closes none of the flaws the audits found in
the `v1.12` line.

## Choose your guide

| You run the node on | Guide | Ways to update |
|---|---|---|
| Linux | **[Linux users guide](migration/linux.md)** | The release archive (x86-64, arm64 or 32-bit ARM), or a build from source |
| macOS | **[Mac users guide](migration/macos.md)** | The release archive (Apple Silicon or Intel), or a build from source |
| Windows | **[Windows users guide](migration/windows.md)** | The release archive, or a build from source |
| Docker | **[Docker users guide](migration/docker.md)** | The registry image, the release tarball, an image built from the release archive, or one built from source |

Every guide takes the same seven steps: stop the node cleanly, install v1.13, rotate the P2P node key, re-check RPC
exposure, start and verify, roll back if you need to, and delete the v1.12 binary or container once the node is
stable.

## If the node runs a release before v1.12.17

To see which release a node runs, ask the running node: `geth attach --exec 'admin.nodeInfo.name'`, with the IPC path
your guide's attach lines use, prints a name that starts with the release, such as `CoreGeth/v1.12.20-stable`.
`geth version` reports the binary on your `PATH`, which need not be the one running.

A release before `v1.12.17` does not schedule Spiral, Ethereum Classic's last upgrade, so a node on one has followed an
obsolete chain since block 19,250,000 and cannot move in place. Resync it instead: remove its chain database as
[Resync from scratch](../operate/maintenance.md#resync-from-scratch) shows, which keeps the node's P2P node key, and
rename that key as step 3 of [your platform's guide](#choose-your-guide) does. Then install the `v1.13` release with
[Installation](../getting-started/installation.md) and start the node, which syncs the chain again from its peers.

## What every node must do

### Rotate the P2P node key

**This step is required.** [CVE-2026-26315](https://github.com/ethereum/go-ethereum/commit/46bee92f9) leaks bits of the
node key across repeated handshakes. `v1.12.21` closed the flaw, but no fix can recall what already leaked, and a key
stays in place through upgrades, so every `v1.12` node rotates.

With the node stopped, rename `geth/nodekey` in the data directory; your guide gives the command. Keep the old file: it
proves which node an old enode ID belonged to. The next start writes a fresh key.

If you start the node with `--nodekey` or `--nodekeyhex`, or set `GETH_NODEKEY` or `GETH_NODEKEYHEX`, take that out too:
it overrides the file.

**Your enode ID changes, so update everything that names this node:**

- **Nodes that list it** in `StaticNodes` or `TrustedNodes`. A running node takes the new ID with no restart, using the
  lines at the end of your guide's step 5. Put the ID in that node's config file too, or it loses the change when it
  restarts.
- **Anyone else who peers with you deliberately.**
- **Monitoring, dashboards and allowlists** that identify the node by enode.

**If this node lists static peers, update its list while it is down.** Static peers are nodes a node keeps connecting
to, such as the rest of a mining pool's fleet. They are under `[Node.P2P]` in the file you pass with `--config`:

```toml
[Node.P2P]
StaticNodes = ["enode://<node ID>@<IP>:30303"]
```

A peer that has already moved has a new ID, so use that. Separate entries with commas. `TrustedNodes` takes the same
form. With no file yet, save these two lines and add `--config` and the file's path to the start command. A file
holding only them changes nothing else.

Editing `static-nodes.json` or `trusted-nodes.json` changes nothing. Every release that can follow Ethereum Classic
ignores them and logs an error
([Why does the node ignore `static-nodes.json`?](../operate/troubleshooting.md#why-does-the-node-ignore-static-nodesjson)).

### Re-check RPC exposure

The node is down, so check these now, wherever the node takes them from: its flags, a `GETH_` environment variable
such as `GETH_HTTP_ADDR` for `--http.addr`, or the `[Node]` section of a `--config` file, as `HTTPHost`, `HTTPModules`,
`HTTPCors`, `WSHost`, `WSModules` and `WSOrigins`:

- `--http.addr` should be `127.0.0.1` unless a trusted proxy terminates in front of it. In a container that publishes
  its ports it must be `0.0.0.0` for the published port to reach it, so check that port instead: publish it on
  `127.0.0.1` only. A container on `--network host` publishes no ports, so there it must be `127.0.0.1`.
- `admin`, `debug` and `personal` do not belong in `--http.api` on an interface another machine can reach, a private
  network included.
- `--http.corsdomain="*"` allows any origin. Name the origins you actually need.
- The same applies to `--ws.addr`, `--ws.api` and `--ws.origins`.

### If you added `--discovery.dns` or `--bootnodes` on `v1.12`

Take them out before the first start on the `v1.13` line. That line reads its own trees and bootnodes by default, and
`--discovery.dns` would leave it no trees for snap peers.

### If your config file came from `dumpconfig`

Before you start the node, open its config file, if it has one, whoever wrote it. A file `dumpconfig` wrote on `v1.12`
holds lines to change first:

- **Delete its `BootstrapNodes`, `EthDiscoveryURLs` and `SnapDiscoveryURLs` lines**, unless you set them yourself on
  purpose. Otherwise the node keeps that release's peer lists, with no message.
- **Delete any `ECBP1100` or `ECBP1100Disable` line.** `v1.12.19` replaced those keys, and every release since
  [stops at the start](../operate/troubleshooting.md#why-does-the-node-stop-with-field-ecbp1100-is-not-defined) on them.
  If a line holds a block number, [set MESS with a flag](#decide-your-mess-setting) instead.

## What changes in v1.13.0

### If you start the node without a network flag

**With no network flag, v1.13.0 runs Ethereum Classic**, and `--mainnet` means the same as `--classic`. If your command
line already names `--classic` or `--mordor`, skip this section.

A v1.12.x node started without a flag ran Ethereum mainnet. If yours did:

- **Data directory.** Without `--datadir`, the node uses `~/.ethereum/classic` on Linux, `~/Library/Ethereum/classic` on
  macOS and `%LOCALAPPDATA%\Ethereum\classic` on Windows, or `%USERPROFILE%\AppData\Roaming\Ethereum\classic` if an
  older `AppData\Roaming\Ethereum` folder exists and is not empty. It does not open the old node's `geth` directory
  beside it.
- **Accounts.** The node reads and writes keyfiles in that directory's `keystore`.
- **Cache.** The default is 1024 MB. `--cache` sets more, up to one third of the machine's memory.
- **An explicit `--datadir`** keeps the chain it holds. A private network initialized with `geth init` keeps its stored
  genesis, and a directory holding Ethereum Classic stays on the current Ethereum Classic configuration.
- **A `--networkid` other than 1** marks a private network, which keeps its v1.12.x defaults: `~/.ethereum` as the data
  directory, no Ethereum Classic bootnodes or discovery trees, and a 30000000 gas ceiling for mining. A private network
  started with neither a network flag nor `--networkid` gets Ethereum Classic's defaults instead, so add `--networkid`,
  or pass `--datadir`, `--bootnodes` or `--nodiscover`, and `--miner.gaslimit`.

### If your chain uses its own genesis or chainspec file

This affects private and custom networks only. v1.13.0 reads three kinds of value in a custom configuration differently
from v1.12.x, matching go-ethereum:

| Value in the file | v1.12.x | v1.13.0 |
|---|---|---|
| A fork block number of 2^63 (9,223,372,036,854,775,808) or more | Active from genesis | Never reached |
| A negative fork block number | Its absolute value | 0 |
| A block number of 2^63 or more in the difficulty bomb delay schedule | Applied from genesis | Never applied |

**If your file holds any of these, change it before you upgrade**, so v1.13.0 applies the rule your chain ran with.
Upgrading every node at once does not avoid this, because a node syncing from genesis would replay past blocks under the
new reading. For example, a fork set to 2^63 to mean "never" ran from genesis under v1.12.x, so set it to 0. A fork set
to -5 ran from block 5, so set it to 5.

### Decide your MESS setting

**An upgrade can change whether your node runs MESS, so set it yourself:** `--mess` turns it on and `--mess=false` turns
it off. Give every node you run the same setting. Under systemd, run `sudo systemctl daemon-reload` after you add the
flag to the unit.

MESS decides which of two competing chains a node keeps during a deep reorganization. It never changes whether a block
is valid. [Which setting fits which operator](../operate/mess.md#which-setting-fits-which-operator) sets out the choice.

To check it, run `admin.ecbp1100Status().enabled` once the node is in sync with at least five peers. Until then it reads
`false` whatever the setting.

### What this migration does not require

- **No resync, from `v1.12.17` on.** Your chain data carries over. A node on an older release
  [resyncs instead](#if-the-node-runs-a-release-before-v11217).
- **No new account keys.** Your keystore is not affected. Rotate account keys only if `admin` or `personal` RPC was
  reachable from an untrusted network.
- **No chain-configuration change.** v1.13.0 runs the same forks as any release from `v1.12.17` on. A release before
  that does not schedule Spiral, Ethereum Classic's last upgrade, so a node on one left that network at block 19,250,000.
- **No data directory change.** Do not rename `geth/` inside it: a node pointed at a renamed directory finds no chain and
  starts a new sync.

## Why this migration

- **Security.** Six CVEs were reported against this client. The earliest v1.12.x releases carry all six; later ones close
  some and not others. v1.13.0 carries every fix, plus a GraphQL query depth limit. The
  [March 2026 audit](../audits/2026-03-security-audit.md) breaks this down by release.
- **Toolchain.** Every v1.12.x archive measured was built on a Go version that is
  [no longer supported](../audits/2026-09-go-toolchain.md). v1.13.0 builds on Go 1.26.
- **Where releases come from.** Release work continues at `ethereumclassic/core-geth`. A node tracking the previous
  repository will not see v1.13.0.
